Flagship work

The problem

Understanding an unfamiliar codebase is slow. Most "AI for code" tools answer from raw text — they have no real model of a repository's structure, dependencies, or how one piece relates to another. The answer sounds plausible without being grounded in the actual graph of the code.

The approach

A staged pipeline that builds an explicit model of the code before any reasoning happens: repository parsing → AST analysis → dependency extraction → dependency graphs → code-relationship mapping → a Neo4j knowledge graph → AI-assisted reasoning on top of that graph → developer-facing visualizations. Accuracy and evaluation infrastructure is part of the architecture, not an afterthought — the goal is a measurable technical moat, not a thin wrapper.

What's actually built

Milestone 1 complete. Staged architecture in active development. The design is deliberately staged so each layer can be evaluated on its own before the next is added.

The problem

Clinical decision-support tools tend to either take the practitioner out of the loop or hand back answers you can't trace. A doctor-facing system needs the opposite: assistance that keeps the clinician in control and makes every recommendation auditable back to its evidence.

The approach & architecture

A FastAPI backend built as additive, API-compatible modules — new capabilities are added without breaking existing endpoints. PostgreSQL with Alembic migrations (schema is never rebuilt with create_all, so changes never drop data). A RAG pipeline retrieves materia-medica evidence and optionally generates with an LLM. A React + TypeScript Doctor Portal organizes features into independent modules; Celery handles background work; the audit log is tamper-evident and the AI layer surfaces matched symptoms, evidence, and sources.

Key decision

Graceful degradation was designed in: no LLM key → it returns the retrieved evidence instead of a generated answer; no vector DB → a local file-backed store; no embeddings model → a hashing embedder. The full clinical flow runs on just Python + Postgres.

The problem

Students and recent graduates struggle to translate a résumé into a clear next step. CareerLens answers three questions: which jobs am I aligned to, which skills am I missing for them, and what should I learn next — in what order?

The approach & architecture

A user can go end-to-end today: register, log in, upload a résumé, and watch a seven-stage analysis pipeline render progressively. Résumé text is extracted (spaCy, PyMuPDF), skills are normalized against a seed dataset, then jobs are scored by an explainable hybrid of three signals — TF-IDF text similarity, skill-graph proximity (networkx), and market demand — with each score exposing its component breakdown. A roadmap generator prioritizes the highest-impact missing skills. React + TypeScript frontend; FastAPI backend using dependency injection for DB sessions and authenticated users, with a clean service layer for parsing, scoring, and roadmap generation.

Honest note

The scoring is intentionally lightweight and rule-based rather than fully semantic or graph-driven — a deliberate MVP foundation. Backend and frontend are both implemented and covered by an automated test suite; what remains is a live public deployment.

The problem

Predict forest-fire and smoke risk from environmental factors — and make it usable, not just a model sitting in a notebook.

The approach

A full tabular-ML pipeline on a CSV dataset of environmental factors: cleaning, feature engineering, and EDA → a Random Forest classifier → evaluation with a confusion matrix, ROC curve, heatmap, and accuracy score → serialization to a .pkl artifact → served over a FastAPI (Uvicorn + Pydantic) inference endpoint → consumed by a React + Vite + TypeScript + Tailwind dashboard with Recharts risk visualizations.

Why it's the cleanest story I have

The point wasn't the model — it was taking a model out of the notebook and putting it behind a real API with a real frontend. This is the tightest end-to-end path from raw data to a served, visualized prediction in my set.

The thesis

Capabilities shouldn't be trapped inside one monolithic AI. ORIGAMI is built around a single idea: every feature reduces to the same primitive — a goal in plain English goes to a planner, which picks tools from a registry, which an executor runs, with memory and context in the loop. So you don't build a hundred features; you build one engine, and every capability is a tool or workflow plugged into an unchanged core. Add a capability = add one file; never touch core/.

Why modular

Get that one property right and the system grows for years; get it wrong — a growing if command == … ladder — and it rots in months. The whole project optimizes for replaceable, extensible, independently-evolvable parts: separation of concerns, adapters over integrations, and platform abstraction underneath.

Direction

The architecture is deliberately shaped so new surfaces and agents — and, further out, navigation and physical/robotics adapters — can be added without rewriting the core. That robotics direction is early design, not a built robot.
